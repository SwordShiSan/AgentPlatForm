# R1.2 local development fixture (IMPLEMENTING)

This is an opt-in, isolated development profile. It is not R1.2 acceptance or cloud-release evidence. Cloud R0 and the R1.1 fixture are unchanged.

## Docker access

Run `python deploy/scripts/docker_preflight.py` from the repository. A successful result reports Linux engine, current context and engine memory only. It never launches/restarts Desktop or switches context.

- `ENGINE_ACCESS_DENIED`: the invoking process lacks pipe/socket permission. Use authorized host execution; restarting Desktop does not fix process permissions.
- `BACKEND_NOT_READY`: Desktop reports running but the engine is unreachable. Inspect Desktop backend/context; optionally use `--wait-seconds 60` during startup.
- `ENGINE_UNREACHABLE`: inspect status/context; an absent pipe alone does not prove Desktop is stopped.
- `WRONG_ENGINE`: a Linux engine is required; select it explicitly outside this script.

Do not use repeated `Start-Process` calls to diagnose engine access. The user's existing running Desktop is preferred. No Windows/WSL service restart, context mutation or other-project container cleanup is performed.

## Fixture commands

Use the repository's pinned Java/Node and package manager to build the backend and frontend first. For this profile only, build Vue with `VITE_CHAT_ENABLED=true`; its default remains disabled. No build may overlap the constrained whole-stack resource acceptance.

Run `python deploy/scripts/chat-local.py prepare`, `build`, `migrate`, `grant`, `seed`, then `start` in that order. `stop` preserves this fixture's volumes and secrets. The project is `agentplatform-r12-local`, PostgreSQL port15442, HTTP port18087; application database `chat`, destructive integration tests use the separately guarded `chat_test` only. Production or R1.1 credentials/data must not be substituted.

`build` packages current backend sources with the Maven Wrapper before Docker COPY (set Java21 JAVA_HOME first). Tests remain a separate mandatory verify gate; packaging does not count as regression. Reproducible jar timestamps cannot prove freshness. `stop` includes the fixture profile so the deterministic provider also stops. After `start` returns healthy, run dependency tests serially rather than racing broker startup. `deploy/probes/chat_failure_acceptance.py provider` uses deterministic error/timeout scenarios and compares physical requests with ledger rows; `outage` reversibly stops only this project's broker/database and restores them in finally blocks.

Secrets are generated in the ignored, protected `.cache/r12-local` directory. The API receives no master key and cannot select credential ciphertext. Only the trusted worker/operator can decrypt. Database records distinguish PLATFORM (explicit model bindings) and USER (exact owner/personal space) with no automatic fallback. The master key remains an external secret. The operator accepts private key files through stdin-created0600 tmpfs input, never key values in arguments. Public APIs do not expose credential management in R1.2.

Default startup uses the local deterministic provider and a sentinel credential. It never imports a real key or calls DeepSeek automatically. Real provider acceptance requires a separately recorded, budget-capped window and the approved private source. The durable acceptance meter is never reset in the application database by this fixture.
