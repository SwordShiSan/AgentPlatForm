# R2 release boundary

R2 is not released by this file. First finish the exact-candidate local gates and protected step→phase→main promotion. Keep GitHub Actions disabled. The cloud continues to use the recorded R1 production identities until the authorized release window succeeds.

The R2 application composition is the existing base + production + R1 HTTP files followed by `compose.r2-http.app.yaml`; environment composition remains base + production + R1 HTTP. Start only API, one worker, gateway and the accepted environment services. Never enable runner, egress, sandbox, test provider, fixed test tools or either recovery acceptance profile. Freeze every effective image/config identity and resource limit in the protected R2 release manifest. Record actual SeaweedFS limits rather than substituting the initial budget; total coexisting limits must stay within2887MiB with768MiB host reserve, including temporary processes.

Required window, each with command/exit/assertion/hash evidence:

1. Read-only inventory of R1 images, exact container IDs/start times/policies, effective Compose, active slots, memory/disk and XFS identity. Record executable R1 rollback commands. Require5GiB root reserve after incoming archives, consistent backup and isolated restore capacity; fail admission without global cleanup. Do not inspect/change DNS or TLS.
2. Stop new writes and drain known work; do not relaunch UNKNOWN calls. Stop R1 and make a consistent PostgreSQL/SeaweedFS/workspace/MQ-definitions/key-version backup. Preserve existing production users and history; no local accounts, model keys or data imports.
3. Import the locally accepted immutable images and verify archive→manifest→config IDs. Run the accepted Flyway migration through V9 using the existing migration role; never edit V1–V8. Apply `config/r2-runtime-grants.sql` as table owner. Verify API denial of SDK state, checkpoint manifest and credential ciphertext. Runtime baseline stays1.
4. Start the same R2 candidate, use the existing HTTP domain and IP/Host, verify identity/chat/SSE, all read-only recovery/reconciliation metadata, tenant isolation and internal endpoint closure. Supplier calls are minimal and separately metered, with quota exhaustion stopping calls. Host stop evidence is generated only for the exact stopped owner/container/image/start time and expired lease; a CLI boolean is insufficient. API/worker never receive a Docker socket or proof-signing key.
5. Observe the fixed candidate for at least1800seconds with dependency faults, sampling memory/swap/disk/connections. Sampling is not a minimum-physical-host or absolute-peak claim. Keep all task-wide deadlines, call limits and UNKNOWN reservations intact.
6. Quiesce, take a consistent backup, then stop the source. Restore serially into independent directories/networks/ports/projects, including credential/key recovery and XFS copy quotas/mount protection. The original XFS UUID stays unchanged. The restore project makes no supplier requests and never runs concurrently with the source stack. Use a dedicated R2 manifest and cleanup-before-first-mutation logic; old R0/R1 fixed schema/table-count/Compose assumptions are not acceptance evidence.
7. Stop R2, restore the recorded R1 application/config identities on the additive schema and verify public health/chat compatibility. Stop R1, restart the same R2 candidate and smoke-test again. On any failure restore R1; never activate the retired legacy business platform.
8. Only all mandatory local and cloud gates PASS permits `production-r2-<sha>` and R2 RELEASED. Otherwise preserve FAIL/NOT_RUN. Archive the change only at the approved closure point; separately hash protected body/evidence copies, retain at least30days and explicitly stop the local fixture profile without deleting volumes/images.

The production preflight/backup/restore driver must be reviewed against this manifest before activation. Merely adding the overlay or migrating a development database is not a cloud release or restore test.
