# Design

Chat uploads are owned by actor and space before conversation creation and are backed by private immutable assets, not a fabricated workspace. Existing file versions remain pinned by fileId/versionId. First task creation binds ordered attachments, immutable source and extraction hashes, configuration, reservation and outbox atomically; changed request content cannot reuse an idempotency key. Each access and physical call rechecks current authorization.

Asset work uses transactional outbox, RabbitMQ confirm, durable claim before ACK, signed runner, bounded renderer, validated output and exact stop receipt before publication. Distinct typed FILE_VERSION and CHAT_ATTACHMENT identities must have valid foreign keys; processing purpose is PREVIEW or TEXT_EXTRACT. Unknown stop or result retains the original slot/reservation and is reconciled without replay. Text extraction uses private S3 outputs with a 2MiB UTF-8 limit; no OCR, macros, network, external links or nested attachments. Existing preview protocol remains compatible.

Context policy freezes model window, task window, output and reserve limits per task and bundle. Input, history, attachment text, tools and observations are counted together. New calls reserve estimated input plus safety and output rather than a full window; actual usage settles against the original reservation and day bucket. Legacy records and old checkpoints remain unchanged. State and checkpoint envelopes are bounded separately and validated before SDK persistence; no silent truncation or summarization.

Vue Query owns server state and Pinia UI/drafts. File, preview, artifact and chat views share immutable versions; a file reference gives no workspace tool privilege. Storage is projected from existing object and quota facts; file trash reuses existing lifecycle. Use lazy paginated virtualized navigation and session-scoped drafts. Changes use existing session, Origin, CSRF and authorization checks.

Release uses an explicit R5 profile and identical locally verified immutable images. During maintenance, user writes remain disabled and a consistent pre-migration snapshot is retained. R4 cannot safely consume V19 tombstone data; rollback to R4 uses the matching pre-upgrade snapshot only before user writes reopen. Never replace new production writes with the old snapshot.
