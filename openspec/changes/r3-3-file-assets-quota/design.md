## Transactions and effects

New adapters continue using docker-java and the existing Nimbus signing extension; do not add a second HTTP/Docker protocol client.
Reserve space bytes and freeze upload metadata before content. Stream private staging with exact size/hash. complete atomically emits outbox; correlated confirm then durable claim/MANUAL ACK precede runner effects. Lock order: space_storage -> existing capacity/auxiliary slots -> workspace -> operation/command/receipt; no network wait in DB transactions. Permissions and fence rechecked before effects and projection commit.
Runner obtains immutable staging with narrowly configured S3 client, streams via Docker exec stdin to fixed helper; helper has no network/S3 credentials/socket and mounts only work. Filesystem write is temp + fsync + atomic rename + parent fsync with original operation receipt. Replacement rechecks physical hash and expected version under write lease. ## Bounded scan and transfer refinement (2026-10-24)
All file transports share one persistent admission slot across API/worker/runner. Admission/release use short transactions; no lease-expiry takeover. A process/close failure retains the slot until exact stopped-instance reconciliation; ordinary timeouts never reset it. S3 network IO remains outside database transactions.
Background SCAN operations reuse the same outbox/claim/ACK/signed runner and exclusive workspace lease, with their own real operation/command identities and no upload/task/environment placeholder. Each scan is a bounded directory page (at most100 entries and28KiB UTF-8 JSON metadata), server-owned parent/cursor/epoch, no file body in the receipt. The fixed helper uses directory handles and nofollow file descriptors, bounded selection, and hashes regular files incrementally; special files/links/NFC collisions reject rather than follow. Every result requires exact stop confirmation before index projection.
A persistent directory cursor continues pages. Entries retain stable UUIDs, independently tracked observed hash/size and scan epoch. Changed/unsealed or missing files become CHANGED/PENDING; the old immutable version remains explicitly historical and is never asserted as current filesystem fact. A directory mutation between pages invalidates the cursor and starts another epoch; do not infer deletion from an incomplete scan. Scanning does not automatically create immutable versions or consume object-version quota. Upload-created/explicit-replaced versions remain the only version sealing path in R3.3; filesystem changes are visibly pending collection.
Query-only reconciliation may project an already stored, exact stopped APPLIED/NOT_APPLIED/SCANNED receipt under the original command/fence after an operation is blocked. It rechecks live authorization, validates immutable object hash where applicable and settles once. It never renews the expired executor, sends another POST, alters a receipt or treats UNKNOWN as success. Unknown receipts retain the original reservation/lease.


## Physical write admission refinement (2026-10-24)
For a new file the fixed Linux helper uses libc renameat2(RENAME_NOREPLACE); a late target is a conflict and is never overwritten. Explicit replacement still requires the original frozen version/hash and the exclusive workspace lease before atomic rename.
Production helper stdin requires a server-derived filesystemDevice field bound by the frozen loop-device policy. Before opening/writing/scanning any user path, fstat of the bound workspace root must match that exact loop device. This supplements the privileged fixed verifier's UUID/prjquota/project checks and rejects fallback writes after a missing mount; no device is passed into the ordinary helper. Direct unit-function tests may use temporary filesystems, but the production CLI has no bypass flag.
Seaweed4.48's official volume -minFreeSpace=5GiB marks low-space volumes read-only. Use that middleware guard plus host preflight/watchdog headroom and bounded single transfer; logical10GiB is not physical capacity. Reference: https://github.com/seaweedfs/seaweedfs/blob/4.48/weed/command/volume.go (minFreeSpace option). No third-party source changes.
Expired staging cleanup first commits a tombstone only for proven non-active, unreferenced uploads; deletion and confirmed absence in the existing private bucket occur outside a DB transaction. Final expiry/refund happens once afterwards. UPLOADING/VERIFYING/UNKNOWN and unresolved file operations are excluded from expiry cleanup. A failed deletion preserves the tombstone and reservation.

## Explicit stdin framing refinement (2026-10-24)
Pinned docker-java3.7.1 HttpClient5 HijackingHttpRequestExecutor copies stdin on a daemon thread without signalling a write-side EOF. Production helper transport therefore uses file-stream-v2: bounded JSON header, exactly the declared payload bytes, then a32-byte binary SHA256 trailer. The helper validates payload and trailer without reading for socket EOF. Existing file-stream-v1 remains a private compatibility adapter with its EOF check; the production runner sends v2 only. Scan commands already use a bounded line and do not depend on EOF. Missing/bad trailer fails before fsync/rename. This is explicit framing within the existing SDK, not a replacement Docker HTTP client or third-party source patch.
A loopback HTTP101 fixture verifies the official core/HttpClient5 path with zero/100MiB inputs and no EOF dependency; it is not actual Engine/XFS evidence. Actual signed runner/helper and native fault gates remain required.
Primary source: https://github.com/docker-java/docker-java/blob/3.7.1/docker-java-transport-httpclient5/src/main/java/com/github/dockerjava/httpclient5/HijackingHttpRequestExecutor.java


## Positive-only upload reconciliation (2026-10-24 implementation detail)
A staged object may finish while its upload metadata commit fails. Add a bounded worker-side UploadReconciliation service, separate from filesystem operation execution. Short typed-Mapper transactions select VERIFYING or expired UPLOADING metadata, fence the old upload status without releasing transport admission or reservation, and CAS the same revision. No network wait is inside that transaction.
The service only reads the original private object through the existing persistent single-transfer admission, checks actual length and full SHA256 with periodic live authorization, and records VERIFIED only after a successful close and matching revision. An old admitted transport still holding the slot prevents reconciliation; expiry never frees it. Fencing prevents the old API owner from passing further stream/end guards or submitting verification. Missing objects, mismatched data, busy admission and unconfirmed stops remain pending; no automatic PUT, delete, refund, complete/outbox or filesystem write is performed. The user may then explicitly complete the same recovered upload. A bounded cursor and capped monotonic backoff avoid unbounded memory/repeated full reads; these are scheduling hints, never ownership or lease facts.
The same living process periodically retries only its already confirmed, failed DB release receipt; this reuses SerialAssetStore's existing stoppedPendingRelease identity and idempotent release journal. It must not release another process, a runner transport requiring its exact receipt, or an unconfirmed close. A dead API/worker with a retained transport remains blocked; lease expiry does not manufacture a stop proof. No new schema or V1–V13 migration changes are needed for this positive-only path. Native object-success/metadata-failure acceptance must verify one original object, unchanged reserved bytes and no automatic filesystem command.

Upload-recovery commit locks idle transfer capacity before workspace/upload rows; runner receipt persistence takes the same transfer row before its workspace locks. Other transfer-only admission/release transactions never acquire workspace rows, preserving the cross-path lock order. No slot is released by the metadata fence.

## Bounded SeaweedFS volume growth (2026-10-24)
The production-shaped fixture stores filer metadata in the default collection as well as assets in their bucket collection. With only two volume slots, default copy_1 growth can consume both slots for metadata before the first non-empty asset. S3 HEAD/empty PUT do not prove data allocation. Configure official `WEED_MASTER_VOLUME_GROWTH_COPY_1=1` and four256MiB volume slots; retain the5GiB disk guard, fixed memory limits and replica000. No third-party source changes or broader S3 permissions are needed. A local same-data comparison returned InternalError before the configuration correction and100MiB success for both scoped application and fixture-admin credentials afterwards. Revalidate the complete HTTP and native chain before stage acceptance; never replay the earlier unknown upload or release its reservation on this evidence alone.
